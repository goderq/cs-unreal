# Архитектура CS-Fusion

## 1. Главная проблема ТЗ: у Fusion 3 нет сервера

Я проверил актуальную документацию, а не память. Результат:

**Хорошая новость.** Photon Fusion 3 **для Unreal существует** — «Fusion
Unreal», UE 5.4+, отдельный SDK, отдельный плагин. Это не Unity-only, как было
у Fusion 1/2. Версия под UE 5.8 есть.

**Плохая новость.** Fusion Unreal 3 — это **shared / distributed authority**.
Цитата из официального intro: Fusion «serverless в том смысле, что ни один
инстанс Unreal не выступает сервером». Gameplay симулируется на самих
клиентах. Комната в Photon Cloud хранит состояние и рассылает обновления, но
**ничего не симулирует**.

Отсюда прямое противоречие с ТЗ:

| Требование ТЗ | Реальность Fusion 3 |
|---|---|
| «dedicated/server-authoritative multiplayer» | сервера нет, dedicated под Fusion невозможен |
| «сервер сам проверяет pickup / damage / inventory» | нет процесса, который мог бы это делать |
| «никогда не доверяй клиенту» | по архитектуре клиенты пишут своё состояние сами |

Photon сам пишет в сравнительной таблице, что ranked competitive PvP —
это случай **для dedicated-сервера**, а shared authority хорош для co-op,
casual, sandbox, social.

### Решение (механика ТЗ сохранена полностью)

**Master Client назначается «сервером».**

Fusion выбирает одного пира комнаты Master Client'ом и автоматически отдаёт
ему владение GameState, переназначая его при миграции. Это единственный
стабильный общекомнатный арбитр, который существует. Весь серверный код ТЗ
(проверка урона, патронов, скорострельности, дистанции подбора, владения
предметом, спавн лута, смерть, респавн, боты, match state) выполняется
**только** там, где `UCSAuthority::IsGameAuthority()` истинно.

Клиенты никогда не пишут это состояние. Они отправляют **запрос** — Fusion
RPC с таргетом `TargetMasterClient` — авторитет валидирует и пишет результат в
реплицируемое свойство объекта, которым владеет он сам. Fusion физически
отбрасывает запись не-владельца, так что подделать чужое состояние клиент не
может.

**Что это даёт:**

- ✅ Единственный победитель при одновременном подборе предмета
- ✅ Клиент не может выдать себе AK-47, патроны, HP
- ✅ Клиент не может назначить себе damage
- ✅ Fire rate, дистанция подбора, ammo — проверяются авторитетом
- ✅ Лут при смерти и при disconnect создаёт только авторитет

**Чего это не даёт:**

- ❌ Игрок, который сам стал Master Client, теоретически может читерить.
  При shared authority от этого нет защиты в принципе.
- ❌ Движение остаётся клиентским (иначе не будет отзывчивости). Speed/teleport
  ловятся пост-фактум проверкой на авторитете, а не предотвращаются.

**Путь к настоящей server authority.** Вся проверка авторитета проходит через
один файл — [`Core/CSAuthority.h`](../Source/CSFusion/Core/CSAuthority.h) — и
через один backend-enum `ECSAuthorityBackend`. Значение `DedicatedServer` уже
объявлено. Когда/если проект переедет на нативный dedicated server (или Photon
выпустит серверный режим), меняется `CSAuthority.cpp`, а не игровой код.

## 2. Второе уточнение: «Fusion vs Unreal Replication» — ложная дихотомия

ТЗ: «репликация через Fusion, а не через обычную Unreal Replication».

Fusion Unreal 3 **переиспользует разметку Unreal как свой авторский слой**:
`UPROPERTY(Replicated)` и `ReplicatedUsing=OnRep_X` сканируются Fusion,
попадают в его `UFusionTypeDescriptor` и уходят по сети через Photon Cloud
собственным `UFusionNetDriver`. `GetLifetimeReplicatedProps` при этом не
вызывается вообще.

То есть `UPROPERTY(Replicated)` в этом проекте — это **и есть** репликация
через Fusion. Transport не Unreal-овский. Мы всё равно объявляем
`GetLifetimeReplicatedProps`, чтобы те же классы продолжили работать, если
проект когда-нибудь переключат на нативный dedicated server.

## 3. Остальные ограничения Fusion 3, влияющие на дизайн

| Ограничение | Последствие для проекта |
|---|---|
| Реплицируемые массивы преаллоцируются, **максимум 64 элемента** | размер инвентаря задаётся через `meta=(FusionArraySize=N)`, слоты фиксированные (Этап 3) |
| RPC **не переигрываются** для late-joiner'ов | всё, что должно пережить вход в комнату, — только в реплицируемых свойствах, не в RPC |
| `AGameMode` выполняется **на каждом** пире локально | любой match-flow код обязан быть под `CS_AUTHORITY_ONLY` |
| `APlayerState` принадлежит **самому игроку** (PlayerAttached) | HP / броня / инвентарь **нельзя** хранить на PlayerState |
| `HasAuthority()` до Fusion-handshake возвращает `true` у всех | читать роль только после `OnObjectReady`, а лучше через `UCSAuthority::CanWrite()` |
| SDK в статусе **Preview** | версионно-зависимый код изолирован в `CSFusionCompat.h` и `CSSessionSubsystem::StartRoomOperation` |
| `FString` в RPC — только **неконстантная ссылка** | `const FString&` и передача по значению отклоняются `FusionPropertyParser`; публичный API берёт `const&` и копирует в локальную переменную |
| Проектный `#if` вокруг рефлексируемых объявлений | UHT пропускает блок целиком, см. §6 |

### Правила написания Fusion RPC

Проверено на исходниках SDK, а не на документации:

1. **Таргет — голый токен-спецификатор**, не выражение:
   `SEND_FUSIONRPC(TargetMasterClient)`, а не
   `SEND_FUSIONRPC(EFusionRPCTarget::SendToMasterClient)` и не `#define`-алиас.
   `FusionMacros.h` определяет макрос как `;`, а токен читает UBT-плагин прямо
   из текста до препроцессора (`FusionUhtFunctionSpecifiers.cs`).
2. **`FString` — только `FString&`.** Ни `const FString&`, ни по значению
   (`FusionPropertyParser.cs:437,447`).
3. **Тело send-функции не писать** — его генерирует плагин. Писать нужно
   только `<Name>_Receive`.
4. **Порядок включений в заголовке:** `"MyClass.fusion.h"` строго **до**
   `"MyClass.generated.h"`.
5. **В .cpp обязателен** (с UE 5.8) `#include UE_INLINE_GENERATED_CPP_BY_NAME(MyClass.fusion)`.
6. **`FUSION_BODY();`** — сразу после `GENERATED_BODY()`.
7. **RPC не переигрываются late-joiner'ам** — всё, что должно пережить вход,
   держать в реплицируемых свойствах.

## 4. Карта владения объектами

| Объект | Fusion Ownership | Кто пишет | Что хранит |
|---|---|---|---|
| `ACSGameState` | `MasterClient` (автоматически) | авторитет | фаза матча, таймер, счёт команд |
| `ACSMatchDirector` *(Этап 2)* | `MasterClient` | авторитет | **HP, броня, инвентарь, ammo, kills/deaths всех игроков** |
| `ACSPlayerState` | `PlayerAttached` (автоматически) | сам игрок | id, ник, команда — только идентификация |
| `ACSCharacter` | `PlayerAttached` | сам игрок | позиция, поза, view pitch |
| `ACSBotCharacter` *(Этап 7)* | `MasterClient` | авторитет | боты симулируются только на авторитете |
| `ACSPlayerInventory` | `MasterClient` | авторитет | слоты инвентаря и экипированный слот одного игрока |
| `ACSWorldPickup` | `MasterClient` | авторитет | лут; подбор арбитрируется, не гонка |
| `ACSProjectile` *(Этап 2)* | `Dynamic` | стрелявший | визуал; урон считает авторитет |

**Почему `ACSMatchDirector`, а не PlayerState:** PlayerState принадлежит
игроку, значит игрок может писать в него что угодно. Единственный способ
сделать HP и инвентарь неподделываемыми в Fusion — держать их в объекте,
которым владеет Master Client. Директор — один актор с массивом записей на
игрока (лимит 64 элемента в самый раз для 16 игроков).

**Почему пикапы `MasterClient`, а не `Transaction`:** `Transaction` отдаёт
решение текущему владельцу. Если владелец — игрок, то при одновременном
подборе двумя игроками решает клиент. Владение Master Client'ом гарантирует,
что предмет получит ровно один.

## 5. Паттерн «запрос → валидация → состояние»

Единый шаблон для всего геймплея. Пример на подборе предмета (Этап 3):

```cpp
// --- Клиент -----------------------------------------------------------
void ACSCharacter::TryPickup(ACSWorldPickup* Pickup)
{
    // Ничего не меняем локально. Только просим.
    RequestPickup(Pickup);
}

void ACSCharacter::RequestPickup(ACSWorldPickup* Pickup)
{
#if CS_WITH_FUSION
    if (UCSAuthority::IsSessionActive(this)) { RpcRequestPickup(Pickup); return; }
#endif
    RpcRequestPickup_Receive(Pickup);   // offline: тот же путь
}

#if CS_WITH_FUSION
SEND_FUSIONRPC(CS_RPC_TO_MASTER)
void RpcRequestPickup(ACSWorldPickup* Pickup);
#endif

// --- Авторитет --------------------------------------------------------
void ACSCharacter::RpcRequestPickup_Receive(ACSWorldPickup* Pickup)
{
    CS_AUTHORITY_ONLY(this);

    if (!IsValid(Pickup) || Pickup->IsClaimed())            return;
    if (FVector::Dist(GetActorLocation(), Pickup->GetActorLocation()) > MaxPickupDistance) return;
    if (!Director->HasInventorySpace(PlayerId))             return;

    Director->AddItem(PlayerId, Pickup->GetItemInstance()); // реплицируемое свойство
    Pickup->ConsumeAndDestroy();                            // единственный победитель
}
```

Обрати внимание: обёртка `RequestX()` даёт один и тот же код-пас онлайн и
offline. Это же позволяет тестировать геймплей до установки SDK.

## 6. Offline-режим — и почему он рантаймовый, а не через `#if`

Первая версия делала SDK опциональным: все объявления Fusion стояли под
`#if CS_WITH_FUSION`, и без плагина проект собирался в offline-режиме.
**Это не работает, и ломается молча.**

UnrealHeaderTool понимает только фиксированный набор условий препроцессора:
`CPP`, `!CPP`, `0`, `1`, `WITH_EDITOR`, `WITH_EDITORONLY_DATA`, `WITH_ENGINE`,
`WITH_COREUOBJECT`, `WITH_HOT_RELOAD`, `WITH_VERSE_VM`, `WITH_VERSE_BPVM`,
`WITH_TESTS`. Любое другое условие получает флаг
`UhtCompilerDirective.Unrecognized`, после чего
`UhtHeaderFileParser.IncludeCurrentCompilerDirective()` **пропускает весь блок**:

```csharp
return !GetCurrentCompositeCompilerDirective().HasAnyFlags(
    UhtCompilerDirective.CPPBlock | UhtCompilerDirective.ZeroBlock |
    UhtCompilerDirective.Unrecognized);
```

Последствия для кода, спрятанного под `#if CS_WITH_FUSION`:

| Что внутри | Что происходит |
|---|---|
| `UPROPERTY` | не регистрируется в рефлексии → GC может собрать объект |
| `UFUNCTION` | не регистрируется → `AddDynamic` падает **в рантайме**, не при сборке |
| `SEND_FUSIONRPC` | не виден UBT-плагину → функция объявлена, но тела нет → ошибка линковки |

Первые два случая компилируются молча и ломаются позже — худший вид бага.

**Как сейчас.** SDK — жёсткая зависимость. `CSFusion.Build.cs` бросает
`BuildException` с инструкцией, если плагина нет. `CS_WITH_FUSION` всегда `1`.
Ни одно рефлексируемое объявление не завёрнуто в проектный `#if`.
В `.cpp` такие директивы легальны (UHT их не парсит), но нужды в них нет.

**Offline-игра при этом сохранилась — как рантаймовый путь.** Если комната не
подключена, `IsSessionActive()` возвращает `false`, `IsGameAuthority()`
возвращает `true`, и обёртка `RequestX()` вызывает свой `_Receive` напрямую
вместо отправки RPC. Один и тот же обработчик работает и в сети, и в одиночном
PIE — что и требовалось для тестирования.

## 9. Разбор бага v0.1.0-alpha: «не могу ходить и двигать мышкой»

В v0.1.0-alpha ввод не работал вообще. Причина — одна строка в
`ACSPlayerController`:

```cpp
PrimaryActorTick.bCanEverTick = false;   // было
```

Весь ввод игрока обрабатывается из тика контроллера:
`APlayerController::TickActor → PlayerTick → TickPlayerInput → ProcessPlayerInput`.
Без тика клавиши доходят и записываются, но никогда не вычисляются.

Почему это было трудно найти: **все остальные звенья выглядели исправными**.
По ходу поиска были проверены и оказались здоровыми:

| Звено | Проверка |
|---|---|
| `InputConfig` в BP, `DefaultPawnClass` в BP геймрежима | чтение ассетов из файла |
| маппинги в `IMC_Default` | 15 штук и в редакторе, и в рантайме |
| класс `PlayerInput` | `EnhancedPlayerInput` |
| контекст в подсистеме | `HasMappingContext = 1` |
| привязки на пешке | `bound 8 input actions` |
| `IsMoveInputIgnored` / `IsLookInputIgnored` | `0 / 0` |
| seamless travel при входе в комнату | биндинги переустанавливаются после travel |
| поведение без триггеров | `SetStateForNoTriggers(IsNonZero ? Triggered : None)` |

Решающим оказался **самотест без зависимости от фокуса окна**: зонд через
`SendInput` ненадёжен (Windows часто не даёт фоновому процессу вывести окно на
передний план), поэтому ввод подаётся прямо в `APlayerController::InputKey` —
тот же вход, что использует платформенный слой. Это дало детерминированное
воспроизведение `moved 0.0 cm`, после чего причина стала очевидна.

### Регрессионные самотесты

Остались в коде и включаются ключами командной строки:

| Ключ | Что проверяет | Успех |
|---|---|---|
| `-cstestinput` | W + мышь через `InputKey`, затем выстрел | `MOVEMENT OK`, `FIRE OK` |
| `-cstestshoot` | находит другого игрока, наводится, стреляет | `DAMAGE OK` |

Самотест перевзводится в `PostSeamlessTravel`, поэтому работает и после
входа в комнату.

### Попутно исправлено в Этапе 2

- Оффлайн `GetLocalPlayerId()` возвращал `0`, а директор считает `0` пустой
  записью — стрельба оффлайн была бы мертва (`NoRecord`). Теперь `1`.
- Регистрация игрока в директоре висела только на Fusion `OnObjectReady`,
  который оффлайн не приходит. Перенесена в `SyncWithDirector` с защитой:
  в сессии регистрация ждёт рукопожатия, иначе удалённая пешка записалась бы
  под локальный id.
- Без меша персонажа удалённые игроки были невидимы, а трассировка
  `ECC_Visibility` пролетала сквозь капсулу (профиль Pawn её игнорирует).
  Добавлены тело-заглушка и блок `Visibility` на капсуле; зона попадания
  определяется по высоте удара, пока нет скелета.
- Mapping context теперь собирается в C++ (`UCSInputConfig::BuildRuntimeMappingContext`),
  а не читается из сгенерированного Python ассета: его видно в diff, и это
  готовая база для переназначения клавиш на Этапе 8.

## 10. Инвентарь (Этап 3)

### Где он живёт

Один актор `ACSPlayerInventory` на игрока, владелец — **Master Client**.

| Вариант | Почему нет |
|---|---|
| на пешке / PlayerState | ими владеет сам игрок (`PlayerAttached`) — модифицированный клиент записал бы себе AK-47, и это бы реплицировалось |
| внутри `ACSMatchDirector` | сетевой массив Fusion ограничен 64 элементами, а 16 игроков × 6 слотов = 96 |

Актор создаёт авторитет при регистрации игрока (`EnsurePlayer`) и уничтожает при выходе (`RemovePlayer`).

### Как предмет передаётся по сети

Как `int32` — индекс в `UCSItemSettings::Items`. Список читается из
`DefaultGame.ini`, поэтому одинаков у всех пиров. Это одно слово вместо строки
или пути к объекту. **Порядок списка — это сетевой формат:** добавлять можно
только в конец, а при перестановке/удалении обязательно поднимать `AppVersion`.

### Стартовый пистолет

В инвентарь не входит никогда. `EquippedSlot == INDEX_NONE` означает «в руках
пистолет». Его магазин хранится в записи директора, у оружия из инвентаря —
в самом слоте (`AmmoInMag`), поэтому выброшенный AK сохраняет патроны.

### Лоадаут

`ACSMatchDirector::GetLoadout(PlayerId)` отвечает на вопрос «что сейчас в руках
и сколько в нём патронов», читая только авторитетное состояние. Этим пользуются
все: проверка выстрела на мастере, локальный гейт на клиенте и HUD — поэтому
они не могут разойтись во мнениях.

### Подбор и спор за предмет

Пикап (`ACSWorldPickup`) принадлежит Master Client. Клиент шлёт запрос
`RpcRequestPickup(AActor*)`, мастер проверяет: предмет существует и не занят,
игрок жив, **дистанция от позиции пешки в представлении мастера**, в инвентаре
есть место. Мастер обрабатывает запросы по очереди, поэтому при одновременном
нажатии первый запрос забирает и уничтожает пикап, а второй находит его
занятым.

У пикапа **нет коллизии по `ECC_Visibility`** — он не должен останавливать пули.
Подсказку «Press E» клиент выбирает сам: ближайший пикап в конусе прицела
в пределах досягаемости с проверкой прямой видимости.

### Разброс выстрела

Теперь накладывается **на мастере**, а не на клиенте, — иначе клиент мог бы
присылать идеально точное направление и стрелять из дробовика без разброса.
Каждая дробина получает свой случайный сдвиг в конусе.

### Точки спавна лута

`ACSPickupSpawnPoint` — несетевой маркер на карте. Есть у всех пиров, но
действует по нему только мастер: создаёт по маркеру пикап, который уже
реплицируется. Левел-дизайнер расставляет лут, не касаясь сети.

### Что осталось на следующие этапы

- Лут при смерти и при выходе игрока — Этап 4 (хук в `RemovePlayer` уже есть).
- Бросок гранат — пока гранаты только подбираются и хранятся.
- Окно инвентаря с drop/inspect — Этап 5 (сейчас выброс по G).

## 11. Лут при смерти и при выходе (Этап 4)

### Смерть

`ApplyDamage` на мастере, когда HP доходит до 0: `DropInventoryAsLoot` забирает
весь инвентарь (`TakeAll`) и раскладывает его пикапами вокруг места смерти.
Стартовый пистолет не затрагивается — его в инвентаре нет. После респауна
у игрока снова только пистолет с полным магазином, а старый лут остаётся на
земле (время жизни — `DroppedItemLifetimeSeconds`).

### Выход и обрыв связи — три независимых детектора

| Детектор | Что ловит | Откуда |
|---|---|---|
| `ACSGameMode::AddInactivePlayer` | штатный выход и обрыв | Fusion вызывает его на каждом пире из `UFusionClient::OnPlayerLeft`; номер игрока — в `PlayerState->SavedNetworkAddress` |
| опрос состава комнаты | игрок `IsInactive` или пропал из списка | `RealtimeClient->GetCurrentRoom()->GetPlayers()` — данные сервера Photon |
| heartbeat | замёрзший клиент, даже если сервер ещё молчит | счётчик на пешке, клиент увеличивает его раз в секунду; 10 с без изменений — отключился |
| пропавшая пешка | страховка на смену мастера | запись есть, пешки нет дольше 8 с |

Все ведут в `RemovePlayer`, и это **намеренно**: при смене мастера новый мастер
может получить уведомление раньше, чем станет авторитетом, и пропустить его.

### Защита от двойного выброса

`RemovePlayer` идемпотентен: первый вызов помечает игрока в `HandledDepartures`,
забирает инвентарь и удаляет запись, повторные вызовы только пишут в лог.
`TakeAll` опустошает инвентарь в том же шаге, поэтому даже прямой повторный
`DropInventoryAsLoot` ничего не создаст. Ушедший игрок не может быть
зарегистрирован заново: номера игроков Photon в комнате не переиспользуются.

**В живом прогоне это сработало не только в тесте:** Photon сообщил об уходе
убитого клиента дважды — сначала «неактивен», через 5 с (PlayerTTL) — «удалён».
Без защиты лут появился бы на карте дважды.

### Место выпадения

Пешка уходящего игрока — `PlayerAttached`, Fusion может уничтожить её раньше,
чем придёт уведомление. Поэтому мастер каждые 0.1 с запоминает позицию каждого
игрока (`LastKnownLocation`) и выбрасывает лут туда.

### Разброс

Без сетевой физики. Мастер вычисляет итоговые точки: кольцо с шагом «золотого
угла» и растущим радиусом, трассировка до пола. На каждом пире предмет локально
«вылетает» по дуге из точки смерти (`DropOrigin`) за 0.45 с. По сети — только
две позиции, выглядит как физика, рассинхрона нет.

### Лимиты

`MaxWorldPickups = 96`. Если выброс превышает лимит, первыми удаляются **самые
старые выброшенные** пикапы; лут, расставленный на карте, не удаляется никогда.

### Ушедший игрок исчезает у всех

Пешка может ещё какое-то время существовать. Когда запись в директоре пропадает
(удаление реплицируется всем), пешка скрывается на каждом пире, чтобы на карте
не стоял замёрзший «призрак».

### Урок тестирования: корневой `CSFusion.exe` — загрузчик

Корневой `CSFusion.exe` (171 КБ) запускает настоящую игру
`CSFusion/Binaries/Win64/CSFusion.exe` дочерним процессом. `Stop-Process -Id`
по PID загрузчика игру **не** убивает. Первые прогоны теста обрыва из-за этого
ничего не проверяли, и я ошибочно заключил, что Photon долго не замечает
пропавшего клиента. Правильный способ — убивать процесс по командной строке:

```powershell
Get-CimInstance Win32_Process -Filter "Name='CSFusion.exe'" |
  Where-Object { $_.CommandLine -like "*clientB.log*" } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

Реальное время обнаружения обрыва Photon в прогоне — около 8 секунд.

## 12. Интерфейс (Этап 5)

### Почему Slate, а не UMG Widget Blueprint

Весь UI написан кодом на Slate (`Source/CSFusion/UI/`). Виджет-блюпринты — это
бинарные `.uasset`: их не видно в diff, их нельзя нормально смёржить, и они
молча ломаются при переименовании C++-свойства. Код на Slate ревьюится как
остальной проект. Виджеты добавляются прямо во viewport, поэтому на них
действует DPI-кривая проекта: вёрстка рассчитана на 1080p и сама
масштабируется на 1440p и 4K.

HUD — Canvas (`ACSHUD`): он и так перерисовывается каждый кадр из
реплицированного состояния, а у Canvas нет затрат на layout. Все координаты
в единицах 1080p, умножаются на `ClipY / 1080`.

| Файл | Что это |
|---|---|
| `UI/CSUIStyle` | палитра, шрифт, стили кнопок, `SCSSelector` (переключатель «< значение >») |
| `UI/SCSMainMenu` | главное меню: PLAY (Quick Match, Create, Join, Session Browser), INVENTORY, SETTINGS, QUIT |
| `UI/SCSSettingsPanel` | настройки; общий для главного и ESC-меню |
| `UI/SCSInventoryPanel` | экран инвентаря: список, иконка, количество, описание, equip/use, drop, inspect |
| `UI/SCSPauseMenu` | ESC-меню: Resume, Settings, Leave Match (с подтверждением) |
| `UI/CSHUD` | HP, броня, прицел, патроны, текущее оружие, быстрые слоты, килл-фид, подсказка подбора, хитмаркер, индикатор урона, таймер |
| `Player/CSMenuPlayerController`, `GameModes/CSMenuGameMode` | карта `Lvl_MainMenu`: без пешки, только меню |
| `Player/CSPlayerControllerMenus.cpp` | открытие/закрытие экранов в матче, режим ввода, фокус |
| `Settings/CSSettingsSubsystem`, `Settings/CSSettingsSave` | загрузка, применение и сохранение настроек |

### Поток игрока

`Lvl_MainMenu` (стартовая карта) → PLAY → подключение к Photon → комната с
привязанной картой `Lvl_Warehouse` → Fusion загружает её у всех. ESC → Leave
Match → **полное** отключение от Photon → снова `Lvl_MainMenu`.

Почему при выходе полное отключение, а не только LeaveRoom: следующий PLAY
идёт тем же путём «подключиться → войти», что и первый, а Fusion-action
отключения (он работает на таймере мира) успевает закончиться до смены карты.

### Исправленная ошибка сессий

До этапа 5 Quick Match вызывал `ConnectAndJoinRoom` с пустым именем. Этот
action SDK всегда делает `JoinOrCreateRoom`, а с пустым именем Photon
**создаёт новую** комнату — два игрока с Quick Match никогда не встречались.
Кроме того, `ConnectAndJoinRoom` отказывается работать, если клиент уже
подключён (а браузер сессий держит подключение). Теперь каждый поток —
«подключиться, затем ровно один вызов комнаты»: `JoinOrCreateRoom` (Create),
`JoinOrCreateRandomRoom` (Quick Match), `JoinRoom` (Join/браузер). Опрос
состояния переведён с таймера мира на core ticker, потому что вход в комнату
меняет карту и таймер мира умирал вместе с ней.

### Браузер сессий

`UCSSessionSubsystem::StartBrowsing` подключается (если нужно), клиент
находится в лобби по умолчанию, и список комнат копируется из
`RealtimeClient::GetCachedRoomList()` в `FCSRoomInfo` при каждом изменении
(`OnRoomListChanged`). Подключение сохраняется, поэтому JOIN из списка
срабатывает сразу, без повторного коннекта.

### Инвентарь в UI — только просмотр и запросы

Экран читает `ACSPlayerInventory`, которым владеет Master Client. Кнопки
вызывают те же запросы, что и клавиши: EQUIP/USE → `RequestSlot`, DROP →
`RequestDropSlot`. Предмет исчезает из списка тогда, когда авторитет его
действительно убрал, — не раньше. В главном меню инвентарь показывает только
пистолет и пустые слоты: вне матча инвентаря нет по дизайну (см. ниже).

### Настройки и сохранение (ТЗ §19)

| Что | Где хранится |
|---|---|
| разрешение, режим окна, лимит FPS, VSync, качество графики | `GameUserSettings.ini` через `UGameUserSettings` |
| чувствительность, инверсия Y, FOV, громкость (общая/музыка/эффекты), переназначенные клавиши | слот сохранения `CSSettings` (`UCSSettingsSave`) |

Значения из файла зажимаются в допустимые диапазоны при загрузке. **Игровой
инвентарь локально не сохраняется вообще** — он существует только в
реплицированном состоянии Master Client'а, подделывать нечего.

Переназначение клавиш: в Settings нажать на клавишу действия и затем новую.
Если клавиша уже занята другим действием, они меняются местами. Цифры 1–7
(слоты) и Backspace зарезервированы. Персонаж подписан на
`OnPreferencesChanged` и сразу пересобирает свой mapping context и FOV.

### Боевые события для HUD

`ACSMatchDirector` собирает попадания за кадр (дробь дробовика суммируется в
одно событие на пару «стрелок → жертва») и рассылает их `RpcCombatEvent`
(TargetAllClients, включая себя). Из них HUD строит килл-фид, хитмаркер
стрелка (красный — убийство, жёлтый — в голову) и индикатор направления урона
у жертвы. Событие косметическое: здоровье и счёт уже лежат в `Records`.

### Проблемы ТЗ, найденные на этом этапе

1. **INVENTORY в главном меню.** Инвентарь по ТЗ должен жить только на
   авторитете и выпадать при смерти/выходе, поэтому вне матча его нет.
   Пункт меню оставлен: он показывает стартовый пистолет, пустые слоты и
   объясняет почему. Если нужен «склад» между матчами — это отдельная
   серверная система (Photon Cloud её не даёт), её нельзя хранить локально.
2. **Громкость музыки и эффектов** сохраняется и показывается, но звуков в
   проекте ещё нет (Этап 6). Общая громкость применяется сразу; музыка и
   эффекты подключатся к Sound Class'ам на Этапе 6.
3. **Иконки предметов** — цветные плашки с сокращением названия (AK, M4…).
   Настоящие иконки — вместе с моделями на Этапе 6.
4. **ESC не ставит матч на паузу** — это мультиплеер; меню забирает только
   ввод локального игрока, о чём оно прямо пишет.

## 13. Модели, анимации, звук, эффекты (Этап 6)

Источники и лицензии всех ассетов — в [docs/ASSETS.md](ASSETS.md).

### Персонаж

- Тело от 3-го лица — Manny или Quinn (по номеру игрока, чтобы игроков было
  легко различить). Его видят все, кроме владельца; владелец видит только
  тень.
- Руки от 1-го лица — тот же манекен, прикреплённый к камере. Голова и ноги
  скрыты через `HideBoneByName`, поэтому руки с оружием поворачиваются вместе
  со взглядом.
- Оружие — `USkeletalMeshComponent` в сокете `HandGrip_R`, отдельно для
  1-го и 3-го лица. Меш, масштаб, стойка и звуки берутся из
  `UCSWeaponDefinition`.
- **Хитбоксы не изменились.** В попадание по-прежнему целится капсула:
  голова, торс и конечности определяются по высоте точки на капсуле. Меши
  чисто визуальные — анимация не может сдвинуть хитбокс так, что два клиента
  разойдутся во мнении, было ли попадание.

### Анимация без Animation Blueprint

`UCSAnimInstance` (`Source/CSFusion/Animation/`) — анимационный инстанс
полностью на C++. Animation Blueprint — это бинарный граф, его нельзя
сгенерировать скриптом, посмотреть в diff или смёржить. Вместо графа у
инстанса свой `FAnimInstanceProxy`, и его `Evaluate()` собирает позу из
сэмплов анимаций через `FAnimationRuntime` — те же примитивы, что под
капотом у узлов графа.

Слои, снизу вверх:

1. Локомоция: idle / ходьба / бег, 8 направлений, общая фаза шага, скорость
   воспроизведения подстраивается под реальную скорость (ноги не скользят)
2. Падение
3. Смерть — клип по направлению, откуда пришёл убивший выстрел, держится на
   последнем кадре
4. Верх тела от `spine_01`: перезарядка (растянута на реальное время
   перезарядки оружия у авторитета), смена оружия, сухой выстрел. От 1-го
   лица вес 0.35: клипы Epic — движения от 3-го лица и иначе уводят оружие
   из кадра
5. Прицел вверх/вниз (аддитивно, только от 3-го лица: от 1-го лица руки и так
   поворачиваются вместе с камерой)
6. Отдача и реакция на попадание (аддитивно)

Всё время считается на игровом потоке в `PreUpdateAnimation`, а прокси
получает готовый снимок. Поэтому `Evaluate`, который может работать в
рабочем потоке, только читает данные.

Какие клипы использовать — Project Settings → CS Animation
(`UCSAnimationSettings`).

### Что и откуда запускает анимацию и звук

Всё это — оформление. Оно работает на каждом клиенте из реплицируемого
состояния и не посылает по сети ничего нового:

| Событие | Источник | Что происходит |
|---|---|---|
| смена оружия | лоадаут в `ACSMatchDirector` | меш оружия, стойка, анимация и звук смены |
| перезарядка | окно перезарядки в записи игрока у авторитета | анимация (растянута на оставшееся время) и звук |
| выстрел своего игрока | нажатие (локальное предсказание) | отдача, анимация, вспышка, звук, трассер — сразу, без ожидания сервера |
| выстрел чужого игрока | `RpcConfirmShot` | то же самое у всех остальных |
| попадание | `RpcConfirmShot` (точка попадания, решённая авторитетом) | дым, искры, след от пули, звук; по игроку — красное облачко |
| урон / убийство | `RpcCombatEvent` | реакция на попадание, анимация смерти по направлению, у стрелка — звук хитмаркера/хедшота/убийства, у жертвы — звук урона |
| подбор | рост реплицируемого инвентаря | звук подбора |
| шаги, приземление | скорость и падение персонажа | звук по пройденному расстоянию; приседание — бесшумно |
| смерть / респаун | флаг `bAlive` в записи | звук |

### Эффекты

`ACSTransientFX` — короткоживущий актёр: один меш (сфера, цилиндр или
«звезда» из двух плоскостей) плюс, при желании, точечный свет. Он сам
масштабируется и гаснет. Эффекты из базовых форм движка и трёх
сгенерированных материалов, а не Niagara: систему Niagara не собрать
скриптом, а этим эффектам не нужно ничего, чего не может масштабируемый
гаснущий меш. Вспышку от 1-го лица видит только стрелок, от 3-го лица — все
остальные.

### Звук

- Все звуки синтезированы (`Scripts/generate_audio.py`) и назначены в
  Sound Class `SC_Music` или `SC_Effects`.
- Громкость музыки и эффектов задаётся прямо в свойствах Sound Class
  (`Properties.Volume`), аудиоустройство перечитывает их каждый кадр. Общая
  громкость — через transient primary volume. (Переопределение через Sound Mix
  было убрано на этапе 7: на незарегистрированном классе движок писал в лог
  строку на каждый кадр.)
- 3D-звуки используют общее затухание `ATT_World` (слышно до ~50 м).
- Клик и наведение в UI — звуки в стиле кнопок Slate.
- В главном меню играет зацикленная музыка.

```
python Scripts/copy_epic_content.py          # ассеты Epic из установки UE
UnrealEditor-Cmd ... -script=Scripts/bootstrap_content.py
python Scripts/generate_audio.py             # WAV в SourceArt/Audio
UnrealEditor-Cmd ... -script=Scripts/bootstrap_stage6.py
```

## 14. Боты (Этап 7)

Код — `Source/CSFusion/AI/`.

| Класс | Роль |
|---|---|
| `ACSBotManager` | держит нужное число ботов: спавнит, выдаёт контроллеры, убирает лишних |
| `ACSBotController` | `AAIController` одного бота: восприятие, дерево поведения, реакция на урон |
| `CSBotBehavior` | собирает Behavior Tree и Blackboard в C++ |
| `CSBTNodes` | узлы дерева: условие по Blackboard, задачи, сервис «мозг» |
| `FCSBotTuning` | параметры сложности (Easy / Normal / Hard) |

### Бот в сетевой модели

- Бот — это тот же `ACSCharacter`, но его владелец в Fusion — **Master
  Client** (`MasterClient`, а не `PlayerAttached`). Поэтому бот не пропадает
  при выходе какого-либо игрока и переходит к новому хосту вместе с ролью
  Master Client.
- Боевой ID бота — `BotId` (от 1000, `CSBots::FirstBotId`), а не владелец
  Fusion. Номера игроков Photon начинаются с 1, так что пересечений нет. У
  каждого бота своя запись у директора и свой инвентарь.
- `ACSBotController` есть только на Master Client. Остальные клиенты видят
  реплицируемую пешку, анимации и эффекты — так же, как у людей.
- Бот действует через `ACSCharacter::BotFire / BotReload / BotPickup /
  BotSelectSlot`. Это **те же обработчики авторитета**, что вызываются по RPC
  от людей: скорострельность, патроны, разброс и дистанция подбора
  проверяются одинаково. Бот не стреляет быстрее и точнее правил.
- **Защита от читов.** RPC-обработчики отклоняют вызов на пешке бота, если он
  пришёл не через `Bot*`. Иначе клиент мог бы послать RPC «выстрел» на
  пешку бота и управлять им.
- Детекторы ухода игрока (сердцебиение, состав комнаты Photon, пропавшая
  пешка) пропускают ID ботов: ботами управляет менеджер.
- Количество и сложность ботов лежат в `ACSGameState` (реплицируется). Их
  задаёт первый авторитет — из меню создателя комнаты или `-bots=N`. Новый
  хост после смены Master Client читает их оттуда и продолжает с теми же
  ботами. Контроллеры — локальные объекты, поэтому новый хост создаёт их для
  ботов, которыми теперь владеет.

### Найденная и исправленная ошибка

Жертва попадания определялась через `UCSAuthority::GetOwningPlayerId(Victim)`
— владельца Fusion-объекта. У всех ботов этот владелец — Master Client,
поэтому выстрел бота в бота наносил урон **хосту-человеку**. Теперь жертва
определяется через `ACSCharacter::GetOwningPlayerId()`, который для бота
возвращает `BotId`. Других обращений к владельцу Fusion вместо ID персонажа
в коде не осталось.

### Behavior Tree и Blackboard без ассетов

Behavior Tree — бинарный граф: его нельзя сгенерировать скриптом или
посмотреть в diff. Поэтому дерево собирается в C++ из тех же классов узлов,
которые создал бы редактор (`UBTComposite_Selector`, `UBTComposite_Sequence`,
декораторы, задачи, сервис), и передаётся в `RunBehaviorTree`.
`UBehaviorTreeManager::LoadTree` инициализирует его так же, как загруженный
ассет.

```
Selector  [сервис: Bot brain, каждые 0.25 с]
|- Sequence "Fight"        [TargetActor задан, прерывает обе стороны]
|    '- Engage target          смотрит на цель, стрейфится, стреляет очередями
|- Sequence "Investigate"  [LastKnownLocation задан]
|    '- Move to LastKnownLocation   идёт к звуку выстрела, месту попадания, месту, где видел цель
|- Sequence "Loot"         [LootTarget задан]
|    |- Move to LootTarget
|    '- Pick up loot
'- Sequence "Patrol"
     |- Find patrol point      случайная достижимая точка по всей карте
     |- Move to PatrolLocation
     '- Pause 0.5–1.5 с
```

Прерывание `Both` на условиях: замеченный враг сразу прерывает лут или
патруль, а потерянная цель сразу останавливает бой.

Сервис «мозг»:
- выбирает ближайшего видимого живого врага;
- экипирует лучшее оружие с патронами (по урону в секунду);
- перезаряжается между боями;
- лечится аптечкой при HP < 65, надевает броню при броне < 50;
- выбирает, за каким лутом идти: оружие лучше текущего, патроны к своему
  оружию, броню или аптечку, если их нет.

### Восприятие

- **Зрение**: радиус 2800 / 3500 / 4500 см по сложности, угол обзора 75°.
- **Слух**: каждый подтверждённый выстрел — шумовое событие на 30 м. Бот
  идёт на звук.
- **Урон**: бот, в которого попали, разворачивается к стрелку, если видит
  его, или идёт туда, откуда стреляли.

### Сложность

| | Easy | Normal | Hard |
|---|---|---|---|
| реакция до первого выстрела | 0.85 с | 0.45 с | 0.25 с |
| ошибка прицела | 4.5° | 2.2° | 1.0° |
| шанс целиться в голову | 0 % | 10 % | 30 % |
| очередь / пауза | 3 / 0.8 с | 4 / 0.45 с | 6 / 0.25 с |

Всё это накладывается поверх обычного разброса оружия, который применяет
авторитет.

### Навигация

`NavMeshBoundsVolume` на всю арену (`Scripts/bootstrap_stage7.py`), навмеш
строится при запуске (`RuntimeGeneration=Dynamic`), запекать нечего.

### Где включаются боты

- Главное меню → PLAY: «Bots» (0–8) и «Bot difficulty» действуют, если
  комнату создаёте вы (Quick Match без открытых комнат или Create Session).
- **PRACTICE VS BOTS** — офлайн-матч без интернета: этот компьютер сам
  авторитет.
- Командная строка: `-bots=N -botdifficulty=easy|normal|hard`.
- Комнаты, созданные через `-room=` без `-bots`, идут без ботов (так
  работают прежние автотесты).

## 15. Анти-чит, оптимизация, тесты, упаковка (Этап 8)

### Что может подделать клиент и что с этим сделано

Каждый игрок владеет своей пешкой (Fusion `PlayerAttached`), поэтому её
положение — это то, что прислал клиент. Всё остальное решает авторитет
(Master Client), и клиент может только просить.

| Попытка | Защита | Где |
|---|---|---|
| Урон, здоровье, патроны, инвентарь | живут только в записях авторитета, клиент их не пишет | `ACSMatchDirector`, `ACSPlayerInventory` |
| Скорострельность выше оружия | интервал выстрела проверяется авторитетом по его часам | `ValidateFire` |
| Выстрел из точки, где игрока нет | начало луча должно быть рядом с глазами пешки на авторитете | `ValidateFire` |
| Подбор предмета издалека | дистанция считается авторитетом от своей копии пешки | `RpcRequestPickup_Receive` |
| **Speed hack** | средняя скорость за окно 1 с сравнивается с пределом (бег × 1.35 + запас на дрожание) | `FCSCheatGuard::ObservePosition` |
| **Телепорт** | один шаг наблюдения больше 6 м и вдвое больше физически возможного — сразу 3 страйка | то же |
| **Флуд RPC** | token bucket на каждый тип запроса: выстрел 20/с (всплеск 30), перезарядка 3/с, подбор 6/с, слот 8/с, выброс 4/с | `FCSCheatGuard::AllowRequest` |

`FCSCheatGuard` — простой C++-класс внутри `ACSMatchDirector`, без UObject,
поэтому его логика покрыта модульными тестами без запуска мира.

Страйки: телепорт весит 3, скорость и флуд по 1. Страйки гаснут со временем
(один за 6 с), поэтому одиночный лаг никого не блокирует. Три страйка
приостанавливают игрока на 10 с: авторитет отклоняет его выстрелы, подборы,
смену слота и выброс (перезарядку оставляем, она ничего не даёт). После
респауна и при первом появлении даётся 2 с на законный «прыжок» через карту.
Боты не проверяются: они и так работают на авторитете.

Проверка стоит первой строкой каждого RPC-обработчика:

```cpp
if (RefuseBotRpc() || !PassesCheatGuard(ECSRequestKind::Fire)) { return; }
```

### Чего этот анти-чит сделать не может (ограничения модели)

- **Читерящий хост.** Master Client и есть авторитет. Если хост подменил
  свою сборку, изнутри Fusion shared authority его не остановить: нужен
  выделенный сервер или серверная валидация (Photon Server Plugins).
  Смягчение: при смене хоста авторитет переходит к другому игроку.
- **Аим-бот и wallhack.** Точное прицеливание неотличимо от навыка, а
  положения всех игроков клиенту нужны для отрисовки. Против этого нужны
  клиентские анти-читы (EAC/BattlEye) и статистика — вне рамок проекта.
- **Мелкий speed hack** в пределах запаса (+35 %) не ловится: меньший запас
  давал ложные срабатывания на лагах.

### Оптимизация

- Попадания считаются по капсуле: у меша тела нет коллизии. Поэтому чужому
  телу вне экрана поза не нужна:
  - `OnlyTickMontagesWhenNotRendered` (монтаж смерти всё равно доигрывается);
  - включён Update Rate Optimization: дальние маленькие тела анимируются реже;
  - FP-руки чужих персонажей не тикают вовсе.
- Своё тело тикает всегда, потому что его скрытая тень должна двигаться.
- Замер `-cstestperf`: 20 с после прогрева, в лог пишутся среднее время кадра,
  p95, p99, худший кадр, время game/render/GPU. Результаты — в
  [TESTS.md](TESTS.md).
- В настройках появился счётчик FPS (**Show FPS**). Вместе с лимитом FPS,
  VSync и пресетами качества он даёт игроку всё нужное для слабых машин.

### Тесты

- `Source/CSFusion/Tests/CSUnitTests.cpp` — модульные тесты UE Automation
  (`CSFusion.Unit.*`) без мира и сети:
  - урон, падение урона с дистанцией, зоны попадания;
  - порядок сложности ботов;
  - ограничения настроек;
  - все сценарии `FCSCheatGuard`.
- `Scripts/run_tests.ps1` запускает модульные тесты и все внутриигровые
  самотесты (`-cstest*`) и печатает сводку PASS/FAIL. Флаг `-Network`
  добавляет анти-чит на двух клиентах через Photon.

### Упаковка

`Scripts/package_release.ps1 -Version X.Y.Z [-Config Shipping|Development]`
делает всё сразу: проставляет версию в `DefaultGame.ini` (она же Photon
AppVersion), собирает, кукает, пакует в IoStore и складывает zip в
`Build/dist`.

| Конфигурация | Для кого | Что в ней есть |
|---|---|---|
| **Shipping** | игроки | без консоли, логов и автотестов; меньше и быстрее |
| **Development** | тестеры | логи, консольные `cs.*`, самотесты, `run_tests.ps1 -Packaged` |

Логов в Shipping нет. Установленный из Launcher движок не позволяет
включить `bUseLoggingInShipping`: для этого нужен движок, собранный из
исходников.

## 16. Полировка до v1.0

### Раунды и таблица счёта

- Фаза матча реплицируется в `ACSGameState`. HUD каждого клиента сам
  показывает баннер при её смене: WARMUP, ROUND STARTED, ROUND OVER с
  победителем. Раньше объявления шли RPC через GameInstance. Первое из них
  отправлялось до того, как Fusion регистрировал GameInstance, и терялось
  (`Missing Function Descriptor`), а на экран они не выводились вовсе.
- Таблица счёта: по `Q` (удержание, клавишу можно переназначить) и сама
  в конце раунда. Игроки и боты отсортированы по убийствам и смертям,
  свой игрок подсвечен.
- В начале раунда директор обнуляет K/D (`ResetScores`). В фазе ROUND OVER
  авторитет отклоняет выстрелы (`ECSFireRejection::MatchOver`), а клиент
  их даже не показывает.
- Исправлено: без комнаты Fusion сообщал 0 игроков, и офлайн-тренировка
  навсегда оставалась в WAITING FOR PLAYERS, без раундов.

### Модели оружия

Шесть разных моделей Quaternius (CC0, [ASSETS.md](ASSETS.md)). Все
параметры подачи лежат в `DefaultGame.ini` → `UCSWeaponPresentationSettings`
и привязаны к имени data asset: модель, масштаб и точки в единицах модели:

| Точка | Для чего |
|---|---|
| `Grip` | хват правой руки |
| `Support` | левая рука: цевьё, помпа или низ рукояти пистолета |
| `Sight` | целик или окуляр; при прицеливании встаёт на ось взгляда |
| `Muzzle` | вспышка и трассер |

Модель ставится в систему координат сокета `HandGrip_R`, в которой держат
оружие анимации Manny: поворот на 90° по yaw, масштаб, `Grip` в начале
координат. Поэтому любая модель лежит в руке так, как этого ждут клипы.
Оружие на земле показывает ту же модель, что и в руках.

### Руки от первого лица

```
камера ─┬─ модель оружия: положение от бедра / в прицеле + процедурные движения
        └─ меш рук: неподвижно ниже и позади взгляда (ArmsOffset)
                      правая кисть — IK, сокет HandGrip_R на Grip модели
                      левая кисть  — IK, ладонь (HandGrip_L) на Support
```

- Оружие крепится к камере, обе руки тянутся к нему через two-bone IK
  (`FCSAnimInstanceProxy::SolveTwoHandIK`). Плечи и локти ведёт клип.
  Поворот левой кисти переносится с оружия Epic, под которое сделан клип,
  на модель.
- Туловище больше не попадает в кадр. Раньше меш рук сдвигался вперёд за
  оружием, и в кадре появлялись плечо и «плавник». От шеи в том числе:
  скрытая масштабом шея стягивала вершины плеч в шип. Теперь скрыта голова.
- Процедурные движения: доставание оружия снизу, перезарядка (опускание и
  наклон), отдача, покачивание при ходьбе, инерция от мыши. Руки следуют за
  оружием через IK.
- От третьего лица оружие остаётся в руке, левая кисть идёт на `Support`
  через IK (`SolveLeftHandIK`).

### Прицеливание

- `SightDistance` задаёт расстояние от глаза до целика, `Sight` лежит точно
  на оси взгляда. Тест `-cstestweapons` проверяет отклонение (0.00 см).
- FOV уменьшается до `AimFovScale`, чувствительность мыши
  пропорциональна FOV, прицельный крест скрыт.
- В прицеливании движение замедляется до 60%, бег отключается.
- Снайперка (`bScope`): модель скрыта, HUD рисует прицел (круглое окно,
  сетка, красная точка), FOV 30% от обычного.

### Плавность чужих игроков

- Позиция чужого игрока приходит по сети шагами. Тело рисуется в
  сглаженной позиции с предсказанием по скорости
  (`ACSCharacter::UpdateRemoteSmoothing`), поворот тоже сглажен.
  Капсула, по которой считаются попадания, не сдвигается.
- Скорость и направление для анимации ходьбы плавно интерполируются, ноги
  не перескакивают между клипами.
- Собственное сетевое сглаживание CMC отключено, чтобы два механизма не
  писали одно смещение меша.

### Тесты

- `run_tests.ps1 -Network` запускает 7 сценариев на двух клиентах: бой,
  спорный подбор, лут при смерти, лут при обрыве, смена хоста с ботами,
  меню и браузер, анти-чит.
- B стартует только после того, как A вошёл в комнату. Тесты A ждут
  соперника (`TestRetryUntil`).
- Самотесты больше не телепортируются: `TestMoveTo` двигает пешку со
  скоростью, допустимой для анти-чита. Прежние телепорты анти-чит этапа 8
  справедливо наказывал.
- Любой `ensure`, `assert` или падение в логе считаются провалом.
