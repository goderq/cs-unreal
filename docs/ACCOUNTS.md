# Аккаунты: вход через Epic (EOS), база Supabase, роли и админка

Вход в игру — только через аккаунт Epic. Пароль игра не видит: весь вход
проходит на стороне Epic, своей формы входа у игры нет. Профиль, ник,
статистика, роли и журнал безопасности хранятся в Supabase.

## Схема работы

```
игра ──1. вход через Epic (при первом запуске окно Epic, потом сохранённая сессия без окна)──► Epic (EOS)
   │◄──── токен доступа Epic (SDK обновляет его сам) ───────────────────────────────────────┘
   │
   └──2. токен Epic──► функция eos-login
                         │ Epic подтверждает токен, выданный именно нашей игре
                         │ находит профиль или создаёт его с ником из Epic
                         │ забаненным отказывает
                         ▼
                   ◄── токен входа на 2 часа + профиль (ник, роль) + статистика
                       (игра тихо обновляет его, пока токен Epic жив)

игра ──3. чтение таблицы лидеров и своей статистики──────► Supabase (PostgREST, только чтение)
хост матча ──4. начало, билеты участников, итог──────────► функция match
модератор / админ ──5. админ-действия─────────────────────► функция admin (AdminService)
```

Игроки ничего не пишут в базу напрямую. Всё, что меняет данные, проходит через
Edge Functions. Функции проверяют токен, а база проверяет роль и права.
Сервисный ключ в игру не попадает никогда.

## 1. Продукт в Epic Dev Portal

1. Открой [dev.epicgames.com/portal](https://dev.epicgames.com/portal) и войди
   своим аккаунтом Epic. Если организации ещё нет, создай её: нужно принять
   бесплатное соглашение разработчика.
2. Нажми **Create Product** и назови продукт, например, `CS-Fusion`.
3. Открой **Product Settings** и запиши:
   - **Product ID**;
   - **Sandbox ID**;
   - **Deployment ID**.
4. **Product Settings → Clients → Add New Client** — клиент для игры:
   - политика **GameClient** (или **Peer2Peer**) с доступом к Epic Account
     Services и Connect;
   - после создания появятся **Client ID** и **Client Secret**.
5. **Рекомендуется (docs/AUDIT.md, B7): отдельный клиент для бэкенда.**
   - Политика **Trusted Server**; его секрет хранится только в Supabase.
   - Функция `eos-login` проверяет токены через этого клиента и сверяет, что
     токен выдан игровому клиенту (`EOS_GAME_CLIENT_ID`).
   - Секрет игрового клиента неизбежно лежит в каждой сборке, поэтому у этого
     клиента должно быть как можно меньше прав.
6. **Epic Account Services → Create Application** (или **Configure**):
   - **Permissions**: как минимум **Basic Profile** (ник);
   - **Brand Settings**: название и ссылка на политику конфиденциальности.
     Без этого у чужих аккаунтов вход завершается ошибкой;
   - **Application → Clients**: привяжи игровой клиент.
7. **EncryptionKey** в портале искать не нужно, Epic его не выдаёт.
   - Это 64 шестнадцатеричных символа, которые ты придумываешь сам:
     `openssl rand -hex 32`.
   - После первых сохранений ключ не меняют: старые данные станут нечитаемыми.

## 2. База Supabase

### 2.1 Миграции

Схема — это упорядоченные миграции в `Backend/supabase/migrations/`. Каждая
безопасна при повторном запуске.

| Файл | Что делает |
|---|---|
| `001_baseline.sql` | Таблицы v1.2: профили, статистика, матчи, таблица лидеров |
| `002_profiles_privacy.sql` | Игроки ничего не пишут и не меняют ник. Публичны только `id`, `nickname`, `created_at` профиля; Epic ID, роли и баны закрыты |
| `003_roles.sql` | Роли `player` / `moderator` / `admin` / `superadmin`; `is_admin` вычисляется из роли |
| `004_security_and_limits.sql` | Журнал безопасности, лимиты частоты запросов |
| `005_match_integrity.sql` | Регистрация матча, билеты участников, проверки отчёта, статистика тренировок |
| `006_admin_service.sql` | Функции AdminService: роль → право → ранг цели → изменение → журнал |
| `007_hardening.sql` | Старая `apply_match_result` удалена; функции доступны только сервисной роли; новые объекты по умолчанию закрыты |

- **Существующая база:** выполни в **SQL Editor** миграции, которых в ней
  ещё нет, по порядку.
- **Новая база:** выполни `Backend/supabase/schema.sql`. Это все миграции
  одним файлом, его собирает `Scripts/build_schema.ps1`.

После миграций выполни `Backend/supabase/tests/security_tests.sql`.
- Тест всегда заканчивается сообщением об ошибке: так все тестовые данные
  откатываются.
- Смотри на текст: `CS-FUSION SECURITY TESTS: N passed, 0 failed.`

### 2.2 Функции

Функции выкладываются из `Backend/supabase/functions/`: в дашборде через
**Edge Functions → Deploy a new function → Via Editor** или через CLI.
Переключатель **Verify JWT with legacy secret** должен быть **включён**.

| Функция | Для чего |
|---|---|
| `eos-login` | Вход: токен Epic → профиль и токен входа на 2 часа |
| `admin` | AdminService: все действия администрации |
| `match` | `start` / `ticket` / `report`: учёт матчей |
| `report-match` | Заглушка: старые сборки v1.2 получают ответ «обновите игру» (410) |

### 2.3 Секреты функций

Задаются в **Edge Functions → Secrets**. Вводит их владелец проекта.

- `EOS_CLIENT_ID`, `EOS_CLIENT_SECRET` — клиент, которым функция обращается к
  Epic (лучше отдельный бэкенд-клиент, п. 1.5).
- `EOS_GAME_CLIENT_ID` — ID игрового клиента, если он отличается от
  `EOS_CLIENT_ID`. Токен, выданный другому клиенту, отвергается.
- `CS_JWT_SECRET` — **Project Settings → JWT Keys → Legacy JWT Secret**.
  Приставку `SUPABASE_` Supabase оставляет за собой, поэтому имя такое.
- `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` Supabase подставляет сам.

### 2.4 Ключи для игры

В игру идут только **Project URL** (**Project Settings → General**) и **anon
public** (**API Keys → Legacy anon, service_role API keys**).
- Нужен именно старый `anon`-ключ: токены игроков подписаны старым секретом.
- Если в проекте отключить старые ключи (**Disable JWT-based API keys**), вход
  перестанет работать (docs/AUDIT.md, C2).

## 3. Ключи в проекте

Скопируй `Config/Backend.ini.example` в `Config/Backend.ini` и заполни:

```ini
[Supabase]
Url=https://ТВОЙ-ПРОЕКТ.supabase.co
AnonKey=eyJ...

[EOS]
ProductId=...
SandboxId=...
DeploymentId=...
ClientId=...
ClientSecret=...
EncryptionKey=...
```

- `Config/Backend.ini` в `.gitignore`: репозиторий публичный.
- Сборочная машина может вместо файла задать переменные окружения:
  `CS_SUPABASE_URL`, `CS_SUPABASE_ANON_KEY`, `CS_EOS_PRODUCT_ID`,
  `CS_EOS_SANDBOX_ID`, `CS_EOS_DEPLOYMENT_ID`, `CS_EOS_CLIENT_ID`,
  `CS_EOS_CLIENT_SECRET`, `CS_EOS_ENCRYPTION_KEY`.

> **Честно о ключах в сборке.** Anon-ключ и ключи игрового клиента EOS есть в
> каждой копии игры: так устроен любой клиент. Это публичная конфигурация, а не
> секреты. Её защищает не скрытность, а права: anon-ключ открывает только
> чтение публичных данных, у игрового клиента EOS минимальная политика.
> Настоящие секреты живут только в Supabase: `service_role`, `CS_JWT_SECRET`,
> секрет бэкенд-клиента EOS.

## 4. Что происходит в игре

### Вход

- **Первый запуск.**
  - Экран «Проверяем сессию Epic…» сменяется кнопкой [SIGN IN WITH EPIC].
  - Кнопка открывает окно Epic (оверлей или браузер).
  - После входа — меню.
- **Следующие запуски.**
  - Сохранённая сессия Epic (EOS persistent auth) входит **без окна и без
    кнопки**, затем сразу открывается меню.
  - Refresh-токен хранит EOS SDK в хранилище учётных данных Windows. Игра его
    не видит, не сохраняет и не пишет в лог.
- **Во время игры.** Токен входа живёт 2 часа.
  - Через 1,5 часа игра тихо обновляет его текущим токеном Epic.
  - Запрос, получивший 401, повторяется один раз после обновления.
  - Если обновить не удалось до конца срока — экран входа с причиной.
- **Выход.**
  - Кнопка **SIGN OUT** на странице PROFILE выходит из игры и из Epic и удаляет
    сохранённую сессию. Следующий запуск снова спросит аккаунт.
  - **SWITCH ACCOUNT** — то же самое, и сразу окно Epic.
- **Нет сети** или сервер недоступен: [PLAY OFFLINE] — тренировка с ботами,
  ничего не записывается. Вернуться в онлайн — [SIGN IN WITH EPIC] в меню.
- **Бан:** вход отклоняется с датой окончания бана.

### Ник

- Первый ник сервер берёт из имени Epic через Epic API.
  - Если имя занято — к нему добавляется `#1234`.
  - Зарезервированные имена (`admin`, `moderator`, …) заменяются на
    автоматическое.
- **Игрок ник не меняет никогда**: ни в интерфейсе, ни через API.
  - Проверено тестами: `update` профиля от игрока отклоняется.
- Ник меняет только администрация через админку:
  - модератор — сбрасывает на автоматический;
  - админ — задаёт любой.

### Статистика

- **Рейтинговая** — матчи онлайн, где минимум два игрока с аккаунтами и нет
  ботов. Только она попадает в таблицу лидеров.
- **Тренировки** — офлайн-матчи и матчи с ботами; учитываются отдельно.

### Учёт матча (functions/match)

1. Хост, начиная матч, регистрирует его (`start`); время старта ставит сервер.
2. Каждый игрок с аккаунтом **своим** входом получает билет участника
   (`ticket`) и отдаёт его только хосту.
3. В конце хост отправляет итог по билетам (`report`). Сервер проверяет:
   - билеты;
   - повторы;
   - длительность по своим часам;
   - лимиты частоты;
   - правдоподобие: убийства в минуту, убийства против смертей, команды и
     победитель, режим, карта.

   Непохожий на правду отчёт записывается, но помечается **подозрительным** и
   никому не засчитывается, пока его не посмотрит модератор.

> **Честно о границах.** Хост — машина одного из игроков, не выделенный сервер.
> - Изменённый клиент хоста может исказить цифры реального матча в пределах
>   проверок правдоподобия.
> - Сговор нескольких аккаунтов не отличить от честной игры.
>
> Билеты гарантируют только одно: статистику нельзя записать на аккаунт,
> который в матче не участвовал. Полностью доверять статистике можно будет
> только с выделенным сервером (docs/AUDIT.md, §3.6).

## 5. Роли и админ-панель

| Роль | Может |
|---|---|
| player | Ничего из админки |
| moderator | Смотреть игроков и матчи; бан до 7 дней, kick (10 мин), снять временный бан; сбросить ник на автоматический; пометить матч подозрительным; журнал — свои действия и автоматические записи |
| admin | Всё, что moderator, плюс: Epic ID в карточке игрока, постоянный бан и снятие любого бана, задать ник, обнулить статистику, аннулировать или одобрить матч, назначить или снять moderator, весь журнал |
| superadmin | Всё, что admin, плюс: назначить или снять admin |

**Правила.**
- Свою роль менять нельзя.
- Действовать над игроком своей роли или выше нельзя.
- `superadmin` через API не выдаётся никогда, только SQL в дашборде.
- Причина обязательна для каждого действия.
- Всё пишется в `security_log`: кто, над кем, что, когда, причина, старое и
  новое значение. IP-адреса и прочие лишние данные не собираются.

**Где проверяются права.**
- Страница **ADMIN** видна только модераторам и выше. Прятать её — лишь
  косметика.
- Каждое действие идёт в функцию `admin`. Та проверяет токен и передаёт в базу
  **его** субъект.
- Базовая функция действия заново читает роль из базы, проверяет право и ранг
  цели, выполняет изменение и пишет журнал — всё одной транзакцией.
- Клиент, открывший панель без роли, получает «forbidden» на каждую кнопку.
  Прямой вызов этих функций через REST API игрокам запрещён — проверено тестами.
- Снятая роль или бан сотрудника действуют сразу.

**Первый superadmin** назначается в дашборде, **SQL Editor**:

```sql
update public.profiles set role = 'superadmin' where nickname = 'ТвойНик';
```

Роль приходит в игру при входе, поэтому после назначения нужно перезапустить
игру.

**Kick.**
- Это короткий бан: 10 минут без входа, билетов и, с Photon Custom
  Authentication (фаза 2), без комнат.
- Выгнать игрока из уже идущей комнаты сервер не может: у Photon Cloud нет
  такого API (docs/AUDIT.md, К8).

## 6. Разработка и тесты

- **Автотесты.** Они не могут входить в Epic, поэтому `Scripts/run_tests.ps1`
  всегда добавляет `-noaccount`: экран входа пропускается, матчи не
  записываются. Тот же ключ удобен для отладки без интернета.
- **Проверка входа по-настоящему** (обращение к Epic и базе):

  ```
  UnrealEditor.exe CSFusion.uproject -game -cstestlogin
  ```

  В лог пишется, каким путём вошли (`saved session, no window` или
  `account portal`), затем `LOGIN TEST BACKEND` и состояние аккаунта.
  Токены в лог не пишутся никогда.
- **Проверка безопасности базы:** `Backend/supabase/tests/security_tests.sql`
  (п. 2.1).
- Если `Config/Backend.ini` нет, игра запускается и на экране входа честно
  сообщает, что аккаунты не настроены. Офлайн-тренировка при этом доступна.
