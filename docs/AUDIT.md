## 0. Коротко

### 0.1 Главное

Пять причин, по которым сейчас нельзя говорить о защищённом мультиплеере и хорошей графике.

1. **RPC может отправить любой участник комнаты на любой объект, а обработчик не знает отправителя (A1).**
   - Клиентский код SDK не проверяет, что отправитель владеет объектом.
   - Поле `Rpc.OriginPlayer` при приёме отбрасывается и до игрового кода не доходит.
   - Худшее следствие: поддельный `RpcGrenadeThrown` заставляет Master Client взорвать **настоящую** гранату с уроном — где угодно и сколько угодно раз.
   - Фильтрует ли такие RPC сервер Photon, из кода не видно. Это первый тест фазы 2.
2. **Master Client определяет, чья это пешка, по полям, которые пишет сам клиент (A2).**
   - `ACSCharacter::GetOwningPlayerId()` возвращает `BotId`, если `bIsBot == true`.
   - Оба поля реплицируются от владельца пешки.
   - Подмена даёт неуязвимость: урон уходит на чужой или несуществующий id.
3. **Статистику матчей можно подделать (A3, A4).**
   - Повторы `profile_id` в отчёте умножают статистику.
   - Отчёты можно отправлять без ограничений.
   - Участников и их профили называют сами клиенты (`RpcIdentify`).
   - Офлайн-матчи против ботов тоже попадают в таблицу лидеров.
4. **Повторный запуск всё равно открывает окно Epic (B2).**
   - `bPreferPersistentAuth=True` стоит в конфиге, но движок читает его только в `AutoLogin()`.
   - Игра вызывает `Login("accountportal")` напрямую, поэтому флаг не действует.
5. **RTX сейчас невозможен в принципе (B14).**
   - Проект рендерит на D3D12 SM5 (в логе: `Using Highest Feature Level of D3D12: SM5`).
   - Аппаратный ray tracing требует SM6.
   - DLSS скачан, но не установлен.

### 0.2 Что уже сделано хорошо и что нужно сохранить

- **Цепочка «запрос → проверка → запись → репликация».**
  - Клиент шлёт запрос, Master Client проверяет его и пишет результат в объект, которым владеет только он. Затем результат реплицируется.
  - Так устроены HP, броня, патроны, деньги, инвентарь, покупки, подбор, смерть и возрождение.
  - `ACSMatchDirector`, `ACSPlayerInventory` и `ACSWorldPickup` принадлежат Master Client (`EFusionObjectOwnerFlags::MasterClient`).
- **`ValidateFire`.**
  - Оружие в руках определяет авторитет, а не клиент.
  - Проверяются: жив ли стрелок, фаза матча, перезарядка, патроны, скорострельность по часам Fusion.
  - Точка выстрела должна быть не дальше 400 см от пешки. Трассировку делает авторитет, разброс тоже считает он.
- **Античит (`FCSCheatGuard`).**
  - Token bucket на каждый тип запроса.
  - Детекция скорости и телепорта.
  - Затухающие страйки и приостановка.
- **Уход игрока обрабатывается идемпотентно**: оружие падает на пол один раз (`HandledDepartures`). Подбор спорного предмета выигрывает ровно один игрок.
- **Секретов в git нет** ни в рабочей копии, ни в истории.
  - Поиск по всем 24 коммитам: JWT, `ClientSecret=`, ключ `service_role`, `CS_JWT_SECRET=`, приватные ключи.
  - `Config/Backend.ini` ни разу не попадал в git.
  - Логи маскируют ключи (`CSBackendConfig.cpp:136`), токены нигде не логируются.
- **Тесты**: 6 unit-тестов, 14 самотестов в игре, 7 сетевых сценариев, скрипт упаковки.
- **Лицензии**: все сторонние ассеты под CC0 и описаны в `docs/ASSETS.md`. Контент Epic не лежит в git.

### 2.3 Путь каждого критического действия

Схема, которая должна соблюдаться везде: **CLIENT REQUEST → VALIDATION → AUTHORITY → STATE CHANGE → REPLICATION**.

| Действие | Как сейчас | Итог |
|---|---|---|
| HP, броня, урон | `RpcRequestFire(origin, dir, bAiming)` → `ValidateFire` → трассировка авторитета из его же позиции пешки, разброс от авторитета → `ApplyDamage` → `Records` → репликация | ✅ схема верная. ⚠ отправитель не проверяется (A1), личность цели (A2), `bAiming`, разброс и отдача (B8) |
| Патроны, перезарядка | `CommitFire` списывает патрон в инвентаре авторитета. `BeginReload` ставит время из данных оружия, завершает перезарядку тик авторитета | ✅ ⚠ A1 |
| Деньги | Пишет только авторитет: награды за убийство и раунд, покупки. Клиент сумму не сообщает никогда | ✅ ⚠ A1: покупка «за другого» |
| Инвентарь, владение оружием | Инвентарь принадлежит Master Client. Клиент присылает только запросы: слот, выброс, подбор, покупка | ✅ ⚠ A1 |
| Подбор | `RpcRequestPickup(actor)` → жив, предмет доступен, дистанция ≤ 350 см, `Claim()` до выдачи | ✅ побеждает один (авторитет однопоточный). ⚠ позиция пешки — слова клиента (B10), A1 |
| Гранаты | `RpcRequestThrow` → `TryThrowGrenade` → `RpcGrenadeThrown` всем → взрыв на авторитете по фитилю | ❌ **приём широковещательного RPC запускает урон на авторитете** (A1) |
| Нож | `RpcRequestMelee` → `AcceptMelee` → трассировка авторитета | ✅ ⚠ A1, NaN (B9) |
| Убийства и смерти | `ApplyDamage` на авторитете | ✅ в пределах доверия к хосту |
| Раунд, счёт команд, итог матча | `ACSGameMode` на авторитете, `ACSGameState` принадлежит Master Client | ✅ в пределах доверия к хосту |

| Движение | Клиент сам двигает свою пешку (так устроен shared authority), авторитет проверяет задним числом | ⚠ по природе модели это CLIENT → STATE. Скорость и телепорт ловятся; высота, стены и возрождение — нет (B10) |

## 3. Отчёт по безопасности

Для каждой находки указано: файл, класс/функция, проблема, почему это проблема, опасность, как исправить, влияние на мультиплеер и на сохранённые данные.

### 3.1 Модель угроз

Кто может атаковать:
- **Изменённый клиент** — самый вероятный противник: память, DLL-инъекция, собственные пакеты.
- **Нечестный хост**: Master Client — такой же игрок.
- **Любой, у кого есть публичные ключи из сборки**: Photon AppId, anon-ключ Supabase, EOS ClientId и ClientSecret из `Backend.ini`.

Выделенного сервера нет. Master Client — это **не** сервер; он лишь «один из игроков, назначенный арбитром».

### 3.2 A — Critical

#### A1. RPC может отправить любой участник комнаты; обработчик не знает отправителя

- **Файлы:**
  - `Plugins/PhotonFusion/Source/PhotonFusion/Private/Types/FusionTypeDescriptor.cpp:464-592` — `UFusionTypeDescriptor::OnSendRPC` и `OnReceiveRPC`;
  - `ThirdParty/Fusion/Types.h:70-93` — `Rpc::OriginPlayer`;
  - все обработчики `*_Receive` в `ACSCharacter`, `ACSMatchDirector` и `UCSGameInstance`;
  - `Core/CSAuthority.h:72-77`: там записано неверное допущение «отправителя нельзя подменить».
- **Проблема.**
  - `OnSendRPC` отправляет RPC на любой объект, владелец не проверяется.
  - `OnReceiveRPC` вызывает `ProcessEvent` без информации об отправителе, хотя в пакете есть `OriginPlayer`.
  - Проект определяет, «кто прислал запрос», через владельца объекта (`GetOwningPlayerId(this)`). Это правда, только если RPC на объект может прислать лишь его владелец.
- **Почему это проблема.** Если сервер Photon сам не отсекает такие RPC:
  - **Гранаты с уроном из воздуха.**
    - Изменённый клиент зовёт `RpcGrenadeThrown(serial, thrower, Frag, origin, vel)` на директоре.
    - Master Client в `RpcGrenadeThrown_Receive` (`CSMatchDirector.cpp:1711`) создаёт гранату.
    - Через 1,6 с `ACSGrenade::Tick` → `ExplodeGrenade` (`CSGrenade.cpp:121-126`) наносит **настоящий урон**, засчитанный на произвольного `ThrowerId`.
    - Нет ни проверки инвентаря, ни лимита частоты.
  - **Ослепление всех.** Поддельный `RpcGrenadeExploded(Type=Flash)` ослепляет всех игроков.
  - **Действия от чужого имени.**
    - `RpcRequestDrop`, `RpcRequestBuy`, `RpcRequestSlot`, `RpcRequestThrow` или `RpcRequestFire`, отправленные на чужую пешку, выполняются как действия её владельца: заставить выбросить оружие, потратить его деньги, сменить ему оружие.
    - Если залить чужую пешку такими запросами, `FCSCheatGuard` приостановит **жертву**.
  - **Кража статистики.** `RpcIdentify` на чужой пешке переписывает `ProfileId` жертвы в таблице Master Client, и её статистика уходит на чужой профиль.
  - **Поддельные события.** `RpcCombatEvent`, `RpcConfirmShot`, `RpcAnnouncement`: ложный килфид, хитмаркеры, звуки для ботов.
- **Опасность:** **критическая**, если сервер Photon не фильтрует такие RPC. **Не проверено**: сервер Fusion скомпилирован, его поведение из кода не видно.
- **Итог фазы 2 (25.09.2026).**
  - Тест `netspoof` показал, что сервер Photon **сам ставит настоящего отправителя**: RPC, где клиент 2 назвал себя клиентом 1, пришёл к Master Client как «от игрока 2».
  - Выбран вариант (а): патч SDK `Scripts/patch_fusion_sdk.ps1` передаёт отправителя в `FFusionRpcOrigin`.
  - Каждый обработчик проверяет отправителя через `CSRpcGuard`: запрос — только от владельца пешки, событие — только от Master Client. Отказ записывается в журнал и даёт страйк.
  - Граната взрывается с эффектом только из реестра гранат, которые авторитет запустил сам.
  - **Закрыто.**
- **Как исправить.**
  1. Даже при фильтрации на сервере: широковещательный RPC не должен запускать логику авторитета.
     - Авторитет ведёт реестр серийных номеров гранат, которые запустил сам.
     - Граната взрывается с уроном только из этого реестра.
  2. Проверка отправителя. Два варианта (см. §9, К9):
     - **(а)** маленький патч SDK (скрипт `Scripts/patch_fusion_sdk.ps1`): передать `Rpc.OriginPlayer` в обработчик. Затем проверка «отправитель == владелец пешки» для запросов и «отправитель == Master Client» для широковещательных событий. Сначала — тест, ставит ли `OriginPlayer` сервер: подделанный `OriginPlayer` должен замениться настоящим.
     - **(б)** без изменений SDK: общий секрет игрок ↔ Master Client через обмен Диффи–Хеллмана по реплицируемым полям плюс HMAC и счётчик в каждом запросе.
  3. Если обработчик вызван не тем, кем должен, — отбрасывать и записывать страйк.
- **Multiplayer:** да. Меняется протокол, поэтому поднимается `AppVersion`, чтобы старые и новые сборки не встречались в одной комнате.
- **Сохранённые данные:** нет.

#### A3. Отчёт о матче позволяет умножать и выдумывать статистику

- **Файлы:**

    - 16 повторов = статистика ×16 за один отчёт.
  - **(б) Выдуманные матчи.**
    - Защита от повторов работает только по паре (`room`, `started_at`). Меняешь любое из двух — новый матч.
    - Лимита частоты нет.
    - `ended_at` присылает клиент.
    - Проверок правдоподобия нет: убийства в минуту, убийства против смертей, команды против победителя.

- **Опасность:** **критическая** для целостности статистики. Подтверждено кодом.
- **Как исправить.**
  - Убирать повторы; каждый профиль учитывается один раз.
  - Время матча — по часам сервера: `start-match` регистрирует матч заранее, `ended_at = now()`.
  - Лимиты частоты по автору и по участникам.
  - Правдоподобие: убийства в минуту, убийства ≤ смерти остальных + боты + гости, согласованность команд и победителя, число игроков, режим и карта из белого списка.

  - Подтверждение участия — «билеты матча» (§5.5).

- **Сохранённые данные:** да — новые таблицы и колонки через миграции; возможна ручная чистка подозрительной статистики.

### 3.6 Что нельзя полностью закрыть без выделенного сервера

Это ограничения Photon Fusion 3 Shared Authority, а не недоработки. Они войдут в `docs/ARCHITECTURE.md`.

- **Нечестный хост.**
  - Master Client — игрок. Изменённый клиент хоста может менять любое авторитетное состояние матча: урон, деньги, результат.
  - Защита — только правдоподобие на бэкенде и флаг «подозрительно».
- **Аимбот и триггербот.**
  - Направление взгляда — слова клиента.
  - Возможна только статистическая детекция: доля хэдшотов, время реакции.
- **ESP и wallhack.**
  - Позиции всех пешек реплицируются всем, отсечения по видимости нет.
  - Interest management в Fusion частично поможет, но не закроет.
- **Движение.**
  - Клиент сам симулирует свою пешку.
  - Небольшое ускорение ниже порога и мелкие правки позиции не отличить от лага.
- **Время.**
  - Попадания считаются по картине мира Master Client; честная компенсация лага требует серверной истории.
- **Итоги матчей.**
  - Нечестный хост может в пределах правдоподобия исказить результат матча, где играли реальные люди.
  - Сговор нескольких аккаунтов не отличить от честной игры.
- **Ключи в клиенте.**
  - Photon AppId, anon-ключ Supabase, EOS ClientId и ClientSecret неизбежно лежат в сборке.
  - Это публичная конфигурация клиента, а не серверные секреты.
  - Серверные секреты — `service_role`, `CS_JWT_SECRET`, секрет бэкенд-клиента EOS — живут только в Supabase.
- **Проверка отправителя RPC** (A1) надёжна ровно настолько, насколько сервер Photon сам ставит `OriginPlayer`. Это проверим тестом.

3. Токен Epic → `eos-login`. Функция проверяет его через `tokenInfo` с `ClientId:Secret`, находит или создаёт профиль, проверяет бан и возвращает JWT на 12 ч (HS256, `role=authenticated`).
4. Меню.

Чего нет: persistent auth, обновления, выхода, смены аккаунта, офлайн-режима, реакции на 401.

### 4.2 Цель (фаза 1)

**Первый запуск:**
1. Экран [ВОЙТИ ЧЕРЕЗ EPIC] → `accountportal` (окно Epic).
2. EOS сохраняет refresh-токен в хранилище Windows. Это делает SDK; игра токен не видит и не хранит.
3. Epic Account ID → `eos-login` → профиль Supabase → JWT в памяти → меню.

**Повторный запуск:**
1. Экран «Проверяем сессию Epic…» → `Login(persistentauth)`: **без окна**.
2. `eos-login` → меню.
3. Кнопка входа появляется, только если persistent auth не сработал.

**Во время игры:**
- Тихое обновление JWT на 80 % срока (токен EOS SDK обновляет сам).
- При 401 — один повторный обмен.
- При потере сессии EOS — снова persistent auth. Не вышло — экран входа с причиной.

**Выход и смена аккаунта:**
- `Logout` в EOS удаляет persistent auth.
- Сброс JWT → экран входа.
- «Сменить аккаунт» = выход + `accountportal`.

**Нет сети:**
- «Нет связи с Epic/сервером» → [ПОВТОРИТЬ] и [ИГРАТЬ ОФЛАЙН (тренировка, без статистики)].

**Что никогда не делаем:**
- не храним пароль;
- не делаем свою форму входа;
- не логируем токены.

**Проверка:**
- Автотест проверяет, что выбран путь `persistentauth`: в лог пишется строка без токена.
- Настоящий повторный запуск без окна проверяет владелец вручную: вход в Epic автоматизировать нельзя, и мы не вводим пароли.

## 5. Бэкенд: RLS, роли, AdminService, миграции, отчёты о матчах

### 5.1 RLS и гранты — итог проверки

| Объект | Сейчас | Нужно |
|---|---|---|
| `profiles` | чтение всех колонок всем; в живой базе игроку ещё разрешён update своей строки | чтение только `id`, `nickname`, `created_at` (или представление); запись только через функции |
| `player_stats`, `matches`, `match_players` | чтение всем, запись только service role | то же; у матчей добавить `ranked`, `suspicious`, `voided` |
| `leaderboard` | представление с правами владельца | `security_invoker = true`, исключить аннулированные матчи |
| `apply_match_result` | SECURITY DEFINER, EXECUTE только у service_role, `search_path` не задан | `set search_path = ''`, повторы убираются, проверки |
| `profiles_guard` | в репозитории ограничивает только роли игроков; в живой базе — всех | миграция |
| `admin_log` | только в репозитории, без причины и старого/нового значения | `security_log` (ниже) |

### 5.2 Роли (RBAC)

Предложение:
- в `profiles` колонка `role`: `player` | `moderator` | `admin` | `superadmin`;
- `is_admin` остаётся вычисляемой колонкой (`role in ('admin','superadmin')`) для совместимости с клиентом v1.2;
- права задаются в коде SQL (функция `cs_has_permission(role, permission)`), а не в таблице: их меньше, и их нельзя «дописать» через данные.

| Право | moderator | admin | superadmin |
|---|---|---|---|
| Список игроков, поиск, детали, матчи игрока | ✔ | ✔ | ✔ |
| Epic Account ID в деталях | — | ✔ | ✔ |
| Временный бан (≤ 7 дней), kick | ✔ | ✔ | ✔ |
| Постоянный бан, разбан | — | ✔ | ✔ |
| Сбросить ник на автоматический | ✔ | ✔ | ✔ |
| Задать ник вручную | — | ✔ | ✔ |
| Пометить матч подозрительным | ✔ | ✔ | ✔ |
| Аннулировать матч, сбросить или очистить статистику | — | ✔ | ✔ |
| Назначить или снять moderator | — | ✔ | ✔ |
| Назначить или снять admin | — | — | ✔ |
| Журнал безопасности | только свои действия и античит | всё | всё |

Правила:
- свою роль менять нельзя;
- действовать над равным или старшим нельзя;
- `superadmin` назначается только SQL в дашборде.

### 5.3 AdminService

Единая функция `admin` работает как маршрутизатор. Каждое действие — SQL-функция `admin_*` с такими свойствами:
- SECURITY DEFINER, `search_path = ''`;
- EXECUTE только у `service_role`;
- в одной транзакции: проверка роли → проверка права → проверка ранга цели → изменение → запись в `security_log`.

Действия:
- `whoami` (verifyAdmin);
- `players.search`, `players.get` (K/D, убийства, смерти, хэдшоты, урон, матчи, победы, время в игре, последние матчи, статус);
- `players.ban` (часы или навсегда, причина обязательна), `players.unban`, `players.kick`;
- `players.set_role`;
- `players.reset_nickname`, `players.set_nickname`;
- `players.reset_stats`;
- `matches.list`, `matches.get`, `matches.flag`, `matches.void`;
- `security.log`.

Kick — см. К8. Mute — голоса и чата в игре нет (К8). Spectate — отложен (К8).

`security_log`:
- `id`, `created_at`;
- `actor_id`, `actor_role`;
- `action`, `target_id`;
- `reason`, `old_value jsonb`, `new_value jsonb`;
- `source`: admin | anticheat | report | system.

IP-адреса **не храним**: для этих задач не нужны, это лишние персональные данные.

### 5.4 Миграции (`Backend/supabase/migrations/`)

Все идемпотентные: `if not exists`, `create or replace`, блоки `do`. Порядок:

| Файл | Что делает |
|---|---|
| `001_baseline.sql` | Текущее состояние v1.2 как база (безопасно на живой базе) |
| `002_profiles_privacy.sql` | Колоночные гранты и публичное представление, revoke update у игроков |
| `003_roles.sql` | `role`, вычисляемый `is_admin`, `cs_has_permission` |
| `004_security_log.sql` | `security_log`, перенос из `admin_log`, если он есть |
| `005_admin_service.sql` | Функции `admin_*` |
| `006_match_integrity.sql` | `ranked`, `suspicious`, `voided`, билеты матча, лимиты, новая `apply_match_result` |
| `007_hardening.sql` | `search_path`, `security_invoker`, итоговые revoke |

`schema.sql` станет сгенерированным снимком: «всё вместе для новой базы».

### 5.5 Честный отчёт о матче

1. **Регистрация матча.** Master Client при старте матча вызывает `start-match(room, mode, map)`. Сервер запоминает время старта и выдаёт `match_id`.
2. **Билеты участников.** Каждый игрок, войдя в матч, запрашивает `match-ticket(match_id, номер игрока в комнате)`. Бэкенд знает игрока по его JWT и выдаёт короткий подписанный билет. Билет уходит **только Master Client** (`TargetMasterClient`), остальные его не видят.
3. **Отчёт.** `report-match(match_id, игроки + билеты)`. Сервер проверяет:
   - билеты;
   - повторы;
   - время по своим часам;
   - лимиты частоты;
   - правдоподобие;
   - `ranked` = есть комната и не меньше двух людей.

   Нарушения → матч записывается с `suspicious = true` и **не** идёт в рейтинг, пока его не посмотрит модератор.

Даже нечестный хост не сможет записать статистику на аккаунт, который не участвовал в матче. Сговор остаётся (§3.6).

## 6. Отчёт по производительности

### Измерено
- Самотест `-cstestperf`, 23.09: редактор `-game`, 960×540, Depot, 9 персонажей (8 ботов), RTX 3050 Laptop (в логе выбран adapter 0).
- Результат: в среднем 4,74 мс (211 FPS), p95 5,95 мс, p99 6,64 мс; игровой поток 4,74 мс, рендер 3,65 мс, GPU 2,20 мс.
- Предел сейчас — CPU (игровой поток, плюс накладные расходы редактора).
- **Это не репрезентативно:** нужен замер упакованной сборки в 1080p и 1440p (фаза 7). Графика сейчас простая, запас по GPU большой, но он исчезнет с новыми картами.

### Риски, видные из кода
- **CPU.**
  - `ACSMatchDirector::Get()` перебирает акторов; вызывается в 85 местах, многие — каждый кадр.
  - `FindPawnForPlayer` — O(n) внутри циклов по записям, то есть O(n²) в тике авторитета.
  - `ACSPlayerInventory::Find` тоже перебирает акторов.
  - `UpdateFocusedPickup` перебирает все предметы каждый кадр.
  - 34 синхронные загрузки (`LoadSynchronous`) в игровом коде — фризы при первом появлении оружия или звука.
  - На каждый выстрел создаются новые акторы-эффекты: 2 меша, динамический материал, свет.
- **GPU.**
  - Lumen (программный) + VSM при Epic по умолчанию.
  - На 4 ГБ VRAM нужна осторожность с новыми картами: бюджет текстур, Nanite, VSM `MaxPhysicalPages`.
- **Сеть.**
  - `RpcIdentify` со строками каждые 10 с всем игрокам.
  - `RpcCombatEvent` передаёт строку на каждое попадание.
  - `RpcConfirmShot` на каждый выстрел всем.
  - Для 10 игроков терпимо, но можно ужать в 2–3 раза.
- **Размер сборки** (v1.2.0): zip 441 МБ; pak 310 МБ; exe 161 МБ; лишние DLL (NNE/onnxruntime, DirectML, ARM64 redist) около 45 МБ.

### Предлагаемые бюджеты (RTX 3050 Laptop 4 ГБ, 1080p, пресет High, 10 игроков)
- Производительность: ≥ 90 FPS в среднем, p95 ≤ 16 мс. VRAM ≤ 3 ГБ. RAM ≤ 6 ГБ.
- Трафик: ≤ 20 КБ/с на клиента.
- Размер: zip ≤ 1,5 ГБ; текстуры 2K максимум (1K для мелочи); trim sheets и общие материалы.
- Цифры уточним после первых замеров.

## 9. Конфликты требований и технические ограничения

Формат каждого пункта: проблема → причина → варианты → выбранное решение → почему.

**К1. Инвентарь и управление.**
- Проблема: запрос v2.0 (23.09) — «убери инвентарь, слоты 1–5». Новое задание — «сохранить inventory и текущее управление».
- Причина: в рабочей копии уже сделана раскладка v2.0.
- Варианты: (а) оставить раскладку v2.0; (б) вернуть экран инвентаря v1.2.
- **Решение: (а).** Раскладка и есть инвентарь, и он принадлежит Master Client. Лут (подбор и выброс оружия) сохранён. Управление v2.0: 1–5, G, E, B.
- Почему: это прямое более раннее решение владельца. Откат уничтожил бы работающую, протестированную систему.

**К2. «Store» и «Inventory» в главном меню.**
- Проблема: постоянной валюты и косметики нет.
- Варианты: (а) Inventory = «арсенал»: оружие, характеристики, раскладка; Store = каталог закупки с ценами и статистикой оружия; (б) настоящий магазин с валютой.
- **Решение: (а).**
- Почему: (б) — это новая экономика с серверной защитой от абуза, большой объём работ и новый риск. Можно сделать позже отдельным решением.

**К3. Warehouse.**
- Проблема: в v2.0 было «удали первую карту, сделай новую», теперь — «переделай Warehouse в логистический комплекс».
- **Решение:** старую карту удалить полностью и построить на её месте новую — логистический комплекс, под тем же именем `Lvl_Warehouse`.
- Почему: выполняются оба требования, ссылки и тесты не ломаются.
- **Итог 26.09 (фаза 4) — сделано.** Склад со стеллажами и антресолями, погрузочная рампа с фурами, контейнерный двор, базы у въездов (docs/MAPS.md).

**К4. Фотореализм Megascans против маленькой сборки и лицензии.**
- Проблема: сэмплы Megascans весят гигабайты, в них текстуры 4K–8K. Лицензия Fab запрещает выкладывать исходники в публичный репозиторий.
- **Решение:**
  - брать ассеты выборочно, текстуры не больше 2K, Nanite, trim sheets;
  - контент Fab — в `.gitignore` (как Mannequins), со скриптом и инструкцией;
  - в сборку он попадает в приготовленном виде, что лицензия разрешает.

**К5. DLSS против «проект собирается после каждого коммита».**
- Проблема: плагин NVIDIA нельзя класть в git.
- **Решение:** интеграция через проверку наличия плагина (Build.cs и проверки во время выполнения). Без плагина проект собирается и работает на TSR/TAA; в меню DLSS не показывается.

**К6. RTX требует SM6.**
- Проблема: время компиляции шейдеров и размер кэша растут; если собирать SM5 и SM6 одновременно, шейдеров станет в два раза больше.
- **Решение:** перейти на SM6. Все GPU с DX12 и актуальными драйверами его поддерживают. RT включается по возможностям GPU с откатом на программный Lumen. Замерить в фазе 5.

**К7. «Обычный игрок не получает admin-UI».**
- Проблема: клиентский бинарник один.
- Причина: код Slate-панели скомпилирован в игру. В нём нет ни данных, ни секретов.
- **Решение:** панель скрыта, а всё реально защищает бэкенд. Отдельная «админская сборка» не нужна: она ничего не добавила бы к безопасности.

**К8. Kick, spectate, mute.**
- Kick: у Photon Cloud нет серверного API, чтобы выгнать игрока из комнаты.
  - **Решение:** kick = короткий бан, плюс Master Client исключает игрока из матча (записи нет, запросы отклоняются), плюс Custom Auth не пускает его обратно.
  - Если хост нечестный, kick в его комнате не сработает — это честно документируем.
- Spectate: вход админа в комнату наблюдателем без пешки возможен, но сейчас не в приоритете. Предлагаю позже.
- Mute: голосового и текстового чата в игре нет — не применимо.

**К9. Проверка отправителя RPC.**
- Проблема: SDK Photon лицензионный и в git не лежит. Правка SDK — «изменение архитектуры вслепую».
- Варианты: (а) минимальный патч, наложенный скриптом: 10–20 строк, передать `OriginPlayer`; (б) HMAC на уровне игры.
- **Решение:**
  - сначала тест, ставит ли сервер `OriginPlayer`;
  - если ставит — (а), это проще и надёжнее;
  - если нет — (б);
  - в любом случае авторитет перестаёт выполнять урон по широковещательным RPC.

**К10. Photon Custom Authentication.**
- Нужно:
  - настройка в Photon Dashboard (делает владелец);
  - параметры авторизации при подключении, которые UE-обёртка не отдаёт.
- **Решение:** патч SDK тем же скриптом, что и в К9, и Edge Function `photon-auth`. Без этого баны в игре не работают (B5).

**К11. Правило «оружие сначала показать».** Остаётся: в фазе 3 — скриншоты и видео до установки.

**К12. Звуки Sonniss.**
- Проблема: лицензия запрещает выкладывать исходные файлы отдельно, то есть в публичный git.
- **Решение:** WAV-файлы Sonniss — в `.gitignore` со скриптом загрузки (`remote_zip.py`); в сборку — в приготовленном виде. Каждый файл скачивается только с разрешения.
